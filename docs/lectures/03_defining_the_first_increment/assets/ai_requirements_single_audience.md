# Предложение AI: документ требований, молча выбравший одну аудиторию

> **Роль в лекции:** контрпример, вводимый после [`ai_requirements_drafts.md`](ai_requirements_drafts.md) — тот же класс задачи, но другой, менее конкретный запрос к AI. Используется в блоке 3 или как материал для семинара, не в блоке 1: центральный пример лекции теперь конструктивный (три честных черновика), этот документ — контраст, показывающий, что бывает при другой формулировке запроса.

## Промпт

```
Опиши требования и критерии приёмки для пилотного этапа проверки данных
экологического мониторинга: нужно проверить качество данных существующих
датчиков и сопоставить их с историей жалоб жителей за последний месяц.
```

Обратите внимание: в отличие от промпта в [`ai_requirements_drafts.md`](ai_requirements_drafts.md), здесь не сказано «набросай по одному варианту для каждой стороны» — запрос не называет аудиторию вовсе.

## Ответ AI (как показывается студентам)

### Пользовательские истории

**US-1.** Как специалист экологической службы, я хочу видеть долю пропущенных измерений по каждому датчику за последние 30 дней, чтобы оценить полноту данных перед анализом.

**US-2.** Как специалист экологической службы, я хочу видеть периоды, где показания датчика статистически расходятся с ближайшей официальной станцией, чтобы выявить потенциально неисправные или некалиброванные датчики.

**US-3.** Как специалист экологической службы, я хочу получить сводную таблицу по всем датчикам с индикацией «надёжный / требует проверки / недостаточно данных», чтобы приоритизировать дальнейшую работу с данными.

**US-4.** Как специалист экологической службы, я хочу сопоставить временные метки жалоб жителей с показаниями ближайшего датчика в соответствующий период, чтобы понять, коррелируют ли жалобы с измеримыми отклонениями.

### Критерии приёмки

- Для каждого датчика рассчитана доля пропущенных измерений за 30 дней.
- Реализован статистический тест расхождения показаний датчика и ближайшей официальной станции.
- Сформирована сводная таблица статусов датчиков.
- Для каждой жалобы за последний месяц найден ближайший по времени и расстоянию датчик и указано его показание.
- Результаты сохранены в структурированном виде (CSV/таблица), пригодном для дальнейшего анализа.

### Технические заметки

Рекомендуется реализовать как аналитический скрипт (Python, pandas) без отдельного пользовательского интерфейса.

## Что скрыто за этим документом (материал для разбора)

Документ структурирован, полон конкретики и на первый взгляд готов к работе. Проблема не в качестве формулировок, а в том, для кого он фактически написан.

- **Все четыре пользовательские истории написаны от лица одной аудитории** — специалиста экологической службы. Промпт не указывал аудиторию явно, но AI молча выбрал её и последовательно провёл этот выбор через весь документ.
- **Руководитель центра нигде не упомянут**, хотя именно ему через шесть недель нужно показать результат горсовету.
- **Жители и общественный совет не упомянуты** ни разу, хотя исходная проблема — их жалобы. US-4 обрабатывает жалобы как входные данные для внутреннего анализа, а не как то, на что нужно дать понятный ответ автору жалобы.
- **Технические заметки незаметно превращаются в архитектурное решение** («реализовать как аналитический скрипт без интерфейса») — документ, который должен был описывать требования, по ходу дела уже выбрал форму реализации.

Сравнение с [`ai_requirements_drafts.md`](ai_requirements_drafts.md) показывает: разница не в возможностях AI, а в том, что было явно попрошено. Запрос «набросай по одному варианту для каждой стороны» дал три честных прочтения; запрос без указания аудитории дал одно, молча выбранное и не помеченное как выбор.

Вопрос для обсуждения: какую именно фразу нужно было добавить в этот промпт, чтобы получить результат, похожий на три черновика вместо одного?
