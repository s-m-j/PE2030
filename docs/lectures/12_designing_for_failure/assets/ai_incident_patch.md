# Предложение AI: срочное исправление во время инцидента

> **Роль в лекции:** показывается в блоке 1 сценария ([../script.md](../script.md)) как уже развёрнутое исправление, принятое под давлением реального инцидента. Разбор рисков открывается в блоке 2.

## Промпт

```
СРОЧНО: станция одного из районов иногда отвечает ошибкой, и всё
задание падает целиком, данные не обновляются вообще ни для одного
района. Прямо сейчас идёт реальный эпизод загрязнения. Добавь
повторные попытки, чтобы задание не падало.
```

## Ответ AI (как показывается студентам — уже развёрнуто)

```python
def fetch_station_data(station_id: str) -> list[Measurement]:
    while True:
        try:
            response = station_api.get(station_id)
            return parse_measurements(response)
        except StationAPIError:
            continue  # повторяем попытку немедленно


def run_daily_collection(district_ids: list[str]) -> None:
    for district_id in district_ids:
        for station_id in get_stations(district_id):
            data = fetch_station_data(station_id)
            store_measurements(station_id, data)
```

### Комментарий AI к изменению

> «Добавил повторные попытки в `fetch_station_data` — теперь при ошибке станции запрос будет повторяться до успеха, вместо того чтобы прерывать всё задание исключением. Задание больше не должно падать целиком из-за одной нестабильной станции».

Изменение развёрнуто немедленно — источник алерта, который увидела команда, действительно перестаёт срабатывать: задание больше не падает с необработанным исключением сразу.

---

## Что произошло дальше (не показывать до блока 2 — материал для разбора)

Задание действительно перестало падать с исключением. Но:

- **Цикл `while True: ... except: continue` не имеет ни ограничения количества попыток, ни задержки между ними.** Пока станция отвечает ошибкой, `fetch_station_data` вызывает её снова и снова, без паузы — то есть система начинает отправлять на нестабильный источник запросы с максимально возможной частотой, дополнительно нагружая именно то, что и так работает плохо.
- **Задание для этой станции зависает бесконечно**, пока станция не восстановится сама — а поскольку `run_daily_collection` обрабатывает районы последовательно в одном потоке, **все районы после зависшего в списке `district_ids` тоже не получают обновлений**, хотя формально исключение больше не возникает и мониторинг не фиксирует падение задания.
- **Идемпотентность не рассмотрена вовсе.** Если станция успела принять и обработать запрос, но соединение оборвалось до получения ответа клиентом, следующая попытка отправит тот же период времени повторно — `store_measurements` не проверяет, не были ли эти данные уже сохранены, и создаёт задвоенные записи.
- **Мониторинг из лекции 7 не срабатывает**, потому что настроен на явную ошибку задания, а не на его зависание — с точки зрения алертинга всё выглядит так, будто ничего не происходит, хотя данные не обновляются уже больше часа.

Это исправление не было злонамеренным или технически безграмотным — оно решает буквально то, что было явно попрошено («не давать заданию падать»), не решая при этом реальной проблемы и создавая новую, менее заметную.

Сравните с изоляцией и деградацией в [`graceful_degradation_example.md`](graceful_degradation_example.md).
