# Контрпример: обратный манёвр Конвея

> **Роль в лекции:** контрпример к [`ai_architecture_only_fix.md`](ai_architecture_only_fix.md), используется в блоке 5 сценария ([../script.md](../script.md)). Начинается не с кода, а с переопределения владения и потоков коммуникации — и только затем согласует архитектурные границы с новой организационной структурой.

## Шаг 1. Явно назвать текущее несовпадение

Прежде чем менять что-либо, фиксируется наблюдение, а не сразу решение:

```text
Наблюдение: изменения, затрагивающие source_adapters + reporting + admin
одновременно, занимают в среднем 21 день против 3 дней для изменений
в одной зоне (по данным истории 40 последних PR).

Текущее владение — неформальное, не задокументированное:
- "зона данных": 3 человека, исторически работали над лекциями 4, 10, 11
- "зона отчётности": 2 человека, подключились в лекциях 7-8
- "зона доступа": 2 человека, пришли после инцидента лекции 13
Пересечение по людям между зонами: 0.
```

## Шаг 2. Определить желаемую архитектуру ДО реорганизации людей

В отличие от AI-плана, здесь желаемые доменные границы формулируются явно как гипотеза, а не выводятся автоматически из текущей связанности кода:

```text
Желаемая архитектура: Data Domain → Reporting Domain, оба используют
общий, переиспользуемый Access Domain (не подчинённый ни одной из
первых двух зон отдельно).
```

## Шаг 3. Переопределить владение и точки пересечения ЛЮДЕЙ, а не только модулей

```text
Новое распределение:
- Data Domain: владение остаётся за "зоной данных" (3 человека)
- Reporting Domain: владение остаётся за "зоной отчётности" (2 человека)
- Access Domain: становится ПЛАТФОРМЕННОЙ командой — 1 человек из "зоны
  доступа" закрепляется как постоянная точка контакта для запросов
  от Data и Reporting, а не согласующая инстанция для каждого PR

Новый процесс: любое изменение, затрагивающее Access Domain,
согласуется с этим одним постоянным контактом на этапе постановки
задачи (не после того, как PR уже готов), а не последовательным
ревью всей "зоны доступа".
```

Это прямо меняет структуру коммуникации: вместо «согласовать с зоной доступа как коллективом в конце» — «обсудить с конкретным человеком в начале».

## Шаг 4. Только теперь — согласовать архитектурные границы

Технические доменные границы (близкие к предложенным AI) вводятся, но **после** того, как определено, кто ими владеет и как происходит координация между владельцами — а не как самостоятельный, оторванный от людей технический план.

```python
# Явные интерфейсы между доменами — то же техническое решение, что и в
# ai_architecture_only_fix.md, но теперь у каждой стороны интерфейса
# есть явный, названный человеческий владелец с определённым процессом
# согласования, а не только модуль в коде.
```

## Шаг 5. Проверка эффекта

Как и в лекции 11, эффект измеряется, а не предполагается: через два месяца после введения нового распределения владения и процесса контакта с Access Domain повторно измеряется среднее время кросс-функционального PR.

```text
Метрика до: 21 день (среднее по 40 PR)
Метрика после (гипотетически, для иллюстрации): 6 дней (среднее по
следующим 15 кросс-функциональным PR)

Если снижение не подтвердится — следующий шаг: разобраться, оказалась
ли причина исключительно организационной, или архитектурные границы
всё же требуют дополнительного пересмотра.
```
