# Предложение AI: чисто архитектурное решение проблемы медленных изменений

> **Роль в лекции:** показывается в блоке 1–2 сценария ([../script.md](../script.md)) как готовый результат. Разбор его односторонности открывается в блоке 2 и продолжается в блоке 3.

## Промпт

```
Кросс-функциональные изменения (затрагивающие приём данных, отчёты
и административный доступ одновременно) идут очень медленно —
недели вместо дней. Проанализируй кодовую базу и предложи
архитектурное решение.
```

## Ответ AI (как показывается студентам)

### Диагноз

> Анализ показывает высокую связанность между модулями `source_adapters`, `reporting` и `admin`: изменения в одном часто требуют правок в двух других из-за неявных зависимостей и отсутствия чётких интерфейсов между ними. Это типичная причина медленных кросс-функциональных изменений.

### Предложенная архитектура

```text
┌───────────────────┐     ┌──────────────────┐     ┌───────────────────┐
│  Data Domain        │────▶│  Domain Events      │────▶│  Reporting Domain   │
│  (source_adapters,  │     │  (SourceRegistered, │     │  (report_builder,   │
│   ingestion)         │     │   MeasurementStored)│     │   templates)         │
└───────────────────┘     └──────────────────┘     └───────────────────┘
                                     │
                                     ▼
                           ┌───────────────────┐
                           │  Access Domain      │
                           │  (auth, audit_log)  │
                           └───────────────────┘
```

### План внедрения

1. Выделить три чётких домена (Data, Reporting, Access) с явными интерфейсами через события, а не прямые вызовы.
2. Перенести общую логику авторизации в отдельный, переиспользуемый Access-домен.
3. Ввести событийную шину для взаимодействия между доменами вместо прямых импортов.
4. Постепенно перенести существующий код по strangler-подходу (см. лекцию 11).
5. Покрыть новые границы характеризующими тестами (см. лекцию 10).

### Заключение AI

> Чёткие доменные границы с явными интерфейсами через события снизят связанность между частями системы и должны ускорить кросс-функциональные изменения, поскольку каждый домен сможет развиваться более независимо.

## Что упущено в этом плане (не показывать до блока 2 — материал для разбора)

Технически план последователен, использует уже знакомые курсу техники (strangler-подход, характеризующие тесты) и полностью адекватен как *архитектурное* решение. Проблема — в том, чего в нём нет.

- **План не упоминает ни одного человека.** Нет ни слова о том, кто будет отвечать за Data Domain, кто — за Reporting, кто — за Access, и как это соотносится с уже сложившимися неформальными зонами команды.
- **Три предложенных домена почти дословно совпадают с тремя уже существующими неформальными зонами** (данные / отчётность / доступ) — то есть план воспроизводит в архитектуре ровно ту структуру, которая уже сложилась в команде, но не решает исходную проблему медленной координации *между* ними: событийная шина технически развязывает код, но не создаёт механизма, по которому три группы людей быстрее согласовывали бы кросс-доменные изменения.
- **Если сегодняшняя структура коммуникации (кто с кем и как часто обсуждает изменения) не изменится**, по закону Конвея новые доменные границы начнут обрастать тем же неявным трением, что и старые модульные границы, — просто на новом техническом слое, при этом потребовав дополнительных усилий на саму миграцию.
- **AI не могло предложить организационную часть решения, потому что не имело к ней доступа** — промпт содержал только вопрос о кодовой базе, и модель ответила ровно на то, что было спрошено, как и в примерах из предыдущих лекций курса.

Сравните с решением, начинающимся не с кода, а с переопределения владения, в [`reverse_conway_example.md`](reverse_conway_example.md).
