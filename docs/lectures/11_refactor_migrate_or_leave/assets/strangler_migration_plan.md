# Контрпример: поэтапная (strangler) миграция реестра источников

> **Роль в лекции:** контрпример к [`ai_big_bang_migration.md`](ai_big_bang_migration.md), используется в блоке 6 сценария ([../script.md](../script.md)). Та же целевая архитектура (конфигурация в БД + административный интерфейс), но без одномоментного риска для шести уже работающих районов.

## Целевая архитектура — та же

`Admin UI → Source Config DB → Adapter Factory`. Разница не в том, куда мы идём, а в том, как туда попадаем.

## Этап 0. Новый механизм принимает только новые источники

`AdapterFactory` разрабатывается и разворачивается, но применяется только к **новым** регистрациям. Все шесть существующих районов продолжают работать через прежний явный реестр `SOURCE_REGISTRY`, без изменений.

```python
def get_adapter(station_id: str) -> SourceAdapter:
    if station_id in SOURCE_REGISTRY:      # шесть существующих районов
        return SOURCE_REGISTRY[station_id]
    return AdapterFactory.build(station_id)  # новые районы — через новый механизм
```

Район №7, если появится на этом этапе, подключается уже через новый механизм — без Pull Request. Это уже снимает основное трение, ради которого затевалась миграция, ещё до переноса единого старого района.

## Этап 1–6. Перенос существующих районов по одному

Для каждого из шести районов, по одному за раз:

1. Пишется характеризующий тест на основе реальных исторических данных этого района (по образцу теста из [лекции 10](../../10_understanding_before_changing/assets/safe_extension_example.md)).
2. Конфигурация района переносится в `source_config`.
3. Запись района удаляется из `SOURCE_REGISTRY`, так что `get_adapter` для него теперь обращается к `AdapterFactory`.
4. Характеризующий тест запускается повторно — расхождение с зафиксированным поведением останавливает перенос этого района до выяснения причины.
5. Изменение разворачивается отдельным, небольшим Pull Request, независимо от переноса остальных районов.

## Этап 7. Удаление старого реестра

`SOURCE_REGISTRY` удаляется только после того, как **все шесть** районов перенесены и подтверждены характеризующими тестами. До этого момента старый реестр и новый механизм существуют одновременно — это ожидаемое, наблюдаемое состояние, а не временный беспорядок, который нужно поскорее убрать.

## Путь назад на каждом шаге

Если перенос района на этапе N выявляет проблему — откатывается только этот один Pull Request (вернуть запись в `SOURCE_REGISTRY`), а не вся миграция целиком. Остальные пять уже перенесённых районов и функциональность для новых районов через `AdapterFactory` не затрагиваются.

## Критерий измерения эффекта

До начала этапа 0 фиксируется исходная метрика: среднее время от заявки района до его подключения (сейчас — по истории последних PR). После завершения этапа 0 (до переноса единого старого района!) эта метрика уже может быть пересчитана для новых районов — если разница не подтверждается, стоит остановиться и разобраться, прежде чем продолжать перенос существующих.

---

## Сравнение усилий

Суммарно поэтапный план требует больше календарного времени и больше отдельных Pull Request, чем план из [`ai_big_bang_migration.md`](ai_big_bang_migration.md) — но ни один момент этого процесса не ставит под риск более одного района одновременно, и в любой точке миграцию можно приостановить, оставив систему в полностью рабочем, наблюдаемом промежуточном состоянии.
