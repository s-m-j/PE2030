# Предложение AI: план полной миграции реестра источников

> **Роль в лекции:** показывается в блоке 1 сценария ([../script.md](../script.md)) как готовый результат — без комментариев. Разбор рисков открывается в блоке 2.

## Промпт

```
У нас шесть районов, каждый со своими датчиками и станцией. Источники
регистрируются вручную в коде — константами и записями в реестре.
Подключение нового района требует отдельного Pull Request каждый раз.
Спроектируй полноценную миграцию: конфигурация источников выносится
в базу данных, добавляется административный интерфейс для регистрации
новых районов без участия разработчиков.
```

## Ответ AI (как показывается студентам)

### Целевая архитектура

```text
┌──────────────────┐     ┌───────────────────┐     ┌──────────────────┐
│  Admin UI          │────▶│  Source Config DB   │────▶│  Adapter Factory   │
│  (регистрация      │     │  (station_id,        │     │  (строит адаптер   │
│   районов)          │     │   source_type,       │     │   на лету по       │
│                     │     │   unit, coefficient) │     │   конфигурации)     │
└──────────────────┘     └───────────────────┘     └──────────────────┘
```

### План миграции

1. **Спроектировать схему таблицы** `source_config` (station_id, source_type, unit, coefficient, is_approximate, calibration_note).
2. **Разработать `AdapterFactory`**, читающую конфигурацию из БД и строящую `SourceAdapter` на лету, заменяя текущие захардкоженные константы `OFFICIAL_STATION` / `LOW_COST_SENSOR` и явный реестр.
3. **Перенести данные всех шести районов** в новую таблицу конфигурации одним скриптом миграции.
4. **Разработать административный интерфейс** (веб-форма) для добавления новых источников без изменения кода.
5. **Удалить старый код реестра и константы** — весь механизм регистрации источников заменяется новым.
6. **Развернуть всё одним релизом.**

### Обоснование AI

> Промежуточное состояние, в котором одновременно существуют старый захардкоженный реестр и новая конфигурация в базе данных, усложнило бы кодовую базу и создало бы путаницу — какой источник данных настроен где. Поэтому миграция выполняется одним релизом: после переноса данных и разработки административного интерфейса старый механизм полностью удаляется. Это даёт чистую, единообразную архитектуру без пережитков старого подхода.

### Оценка усилий

Разработка: ~3 недели. Тестирование: ~1 неделя. Развёртывание: один релиз, все шесть районов одновременно.

## Что скрыто за этим планом (не показывать до блока 2 — материал для разбора)

Архитектура целевого состояния технически разумна — конфигурация в базе данных вместо констант в коде действительно снижает трение для новых районов в долгосрочной перспективе. Проблема не в целевом состоянии, а в способе туда попасть.

- **Все шесть районов переносятся одновременно, одним релизом.** Если `AdapterFactory` содержит ошибку, недоступную старому явному реестру (например, в порядке применения коэффициента или в интерпретации `is_approximate`), под ударом окажутся сразу все районы, а не один.
- **Отката к прежнему реестру не предусмотрено.** «Старый код реестра удаляется» на шаге 5 означает, что при обнаружении проблемы после релиза единственный путь — экстренно чинить новый механизм в бою, а не вернуться к заведомо работавшему.
- **Ни один шаг плана не включает характеризующие тесты**, аналогичные тем, что команда уже использовала при подключении Северного района в лекции 10 — притом что риск скрытой регрессии здесь не меньше, а больше: меняется сразу весь механизм, а не одна функция.
- **Обоснование «промежуточное состояние усложнило бы код» рассматривает только сложность кода**, не сопоставляя её с риском одномоментного изменения для уже работающей системы, от которой зависят шесть районов и их жители.
- **План не содержит ни одного критерия, по которому команда узнает, что миграция была успешной** — только описание того, что должно быть построено, без определения, как измерить, действительно ли новый механизм снизил трение при подключении района №7.

Сравните с тем, как та же целевая архитектура достигается поэтапно, без риска для уже работающих районов, в [`strangler_migration_plan.md`](strangler_migration_plan.md).
