# Успешный пример: узко очерченное делегирование одного шага

> **Роль в лекции:** второй контрпример к [`ai_generated_giant_pr.md`](ai_generated_giant_pr.md), используется в блоке 7 сценария ([../script.md](../script.md)) вместе с [`decomposed_pr_example.md`](decomposed_pr_example.md). В отличие от него, здесь не тот же PR, разделённый постфактум, а задача, изначально поставленная узко — новый недорогой датчик другого типа, который команде нужно подключить параллельно с работой над ADR из лекции 4.

## Промпт

```
Реализуй только адаптер источника для нового типа датчика (PM_LASER,
диапазон 0-500 µg/m³, прямое измерение PM2.5 без пересчёта). Он должен
соответствовать интерфейсу SourceAdapter из source_adapters.py — см.
файл целиком для контракта. Обязательно покрой тестами: обычное
значение, нулевое значение, значение на границе диапазона, ошибочная
единица измерения. Не трогай ничего за пределами source_adapters.py —
ни classify(), ни другие адаптеры, ни тесты для них.
```

## Ответ AI

Один PR, один новый файл не создаётся — добавление в существующий `source_adapters.py`:

```python
PM_LASER_SENSOR = SourceAdapter(
    source_type="pm_laser_sensor",
    unit="µg/m³",
    to_reference_scale=lambda v: v,
    is_approximate=False,
    calibration_note="прямое лазерное измерение PM2.5, эталонная шкала, паспортная точность ±3 µg/m³",
)
```

Тесты (4, все новые, ничего не изменено в существующих):

```python
def test_pm_laser_sensor_typical_value():
    assert PM_LASER_SENSOR.to_reference_scale(22.0) == 22.0

def test_pm_laser_sensor_zero():
    assert PM_LASER_SENSOR.to_reference_scale(0.0) == 0.0

def test_pm_laser_sensor_boundary():
    assert PM_LASER_SENSOR.to_reference_scale(500.0) == 500.0

def test_pm_laser_sensor_wrong_unit_raises():
    bad = Measurement("S9", "PM2.5", 10.0, "index_0_500", datetime.now())
    with pytest.raises(ValueError):
        to_comparable_scale(bad)  # существующая функция, не изменена
```

**Сообщение к PR:** `Add PM_LASER_SENSOR adapter per new sensor type request; no changes outside source_adapters.py`

## Материал для разбора

Ревью занимает несколько минут: изменение ограничено одним файлом, интерфейс соблюдён, тесты покрывают ровно то, что было явно попрошено, включая граничные случаи. Единственное замечание при ревью — стилистическое: `calibration_note` у этого адаптера длиннее, чем у остальных, стоит сократить для единообразия. Ничего похожего на кеширование, переформатирование или переименования не появилось — потому что об этом не просили, а задача была явно ограничена.

- **Задача была узкой с самого начала**, а не разделена на части постфактум, как в [`decomposed_pr_example.md`](decomposed_pr_example.md). Оба подхода работают, но этот показывает, что хорошая декомпозиция может быть спроектирована заранее, а не только восстановлена после того, как большой PR уже стал проблемой.
- **Явный интерфейс (контракт `SourceAdapter`) избавил AI от необходимости угадывать границы.** Задаче было куда соответствовать — это резко снизило пространство для «заодно улучшу».
- **Явный запрет («не трогай ничего за пределами файла») был выполнен буквально** — та же способность AI следовать инструкции, которая в [`ai_generated_giant_pr.md`](ai_generated_giant_pr.md) привела к смешению scope, здесь привела к его отсутствию, потому что инструкция была явной.

Вопрос для обсуждения: какие из шагов первого, большого PR можно было бы заранее сформулировать так же узко, как этот, — и что помешало сделать это сразу?
