# Предложение AI: инструкция по развёртыванию

> **Роль в лекции:** показывается в блоке 1 сценария ([../script.md](../script.md)) как готовый результат — без комментариев. Разбор пробелов открывается в блоке 2.

## Промпт

```
Мне нужно быстрее всего развернуть наш скрипт сопоставления жалоб на
сервере ИТ-отдела мэрии, чтобы он запускался раз в неделю (сводка для
специалиста) и раз в месяц (отчёт для общественного совета). Дай
пошаговую инструкцию.
```

## Ответ AI (как показывается студентам)

### Шаг 1. Скопировать код на сервер

```bash
scp -r ./pilot_increment user@eco-server:/home/user/pilot_increment
```

### Шаг 2. Прописать конфигурацию прямо в скрипте

```python
# config.py
STATION_API_KEY = "a8f3-9c21-...redacted..."
STATION_API_URL = "https://stations.example.gov/api/v1"
COMPLAINTS_DB_PASSWORD = "PilotDB2026!"
REPORT_EMAIL_SMTP_PASSWORD = "smtp-pass-here"
```

### Шаг 3. Настроить cron

```bash
ssh user@eco-server
crontab -e
```

```cron
0 9 * * 1   /home/user/pilot_increment/run_weekly_summary.sh
0 9 1 * *   /home/user/pilot_increment/run_monthly_report.sh
```

### Шаг 4. Проверить, что работает

```bash
/home/user/pilot_increment/run_weekly_summary.sh
# письмо со сводкой пришло специалисту — готово!
```

### Итог

> Готово! Скрипт теперь будет автоматически запускаться каждую неделю и каждый месяц. Если понадобится обновить логику — просто отредактируйте файлы на сервере и всё продолжит работать с новой версией.

---

## Что скрыто за этой инструкцией (не показывать до блока 2 — материал для разбора)

Инструкция технически рабочая — если выполнить все четыре шага, письма действительно начнут приходить. Проблема не в том, что она не работает, а в том, чего в ней нет.

- **Учётные данные записаны прямо в файле на сервере** — `STATION_API_KEY`, пароли к базе жалоб и SMTP. Любой, у кого есть доступ к серверу или к резервной копии этого файла, получает доступ ко всем секретам сразу. Это прямо противоречит требованию ИТ-отдела из лекции 2 не создавать новых рисков безопасности.
- **Версия на сервере не связана с репозиторием.** «Обновить логику — отредактировать файлы на сервере» означает, что через месяц никто не сможет с уверенностью сказать, соответствует ли код на сервере тому, что прошло ревью в лекции 6, или кто-то внёс правку прямо на месте.
- **Нет уведомления о сбое.** Если `run_monthly_report.sh` завершится с ошибкой (например, недоступен источник данных), cron просто не отправит письмо — никто в команде не узнает об этом, пока кто-то не заметит отсутствие отчёта.
- **Нет отличия «успешно завершилось» от «результат верный».** Шаг 4 проверяет только то, что письмо пришло хотя бы раз, — не то, что оно продолжит приходить корректным по содержанию каждую неделю.
- **Отката нет.** Если после ручного редактирования файлов на сервере отчёты стали неверными, единственный способ «откатиться» — вспомнить и вручную восстановить, как код выглядел раньше.

Ни одна из этих проблем не мешает скрипту сработать один раз — именно поэтому демонстрация «письмо пришло, всё работает» на шаге 4 создаёт ложное чувство завершённости.

Сравните с контролируемой альтернативой в [`safe_delivery_plan.md`](safe_delivery_plan.md).
