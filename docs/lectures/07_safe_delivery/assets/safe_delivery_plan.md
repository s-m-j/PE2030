# Контрпример: минимально достаточная контролируемая поставка

> **Роль в лекции:** контрпример к [`ai_deploy_script.md`](ai_deploy_script.md), используется в блоке 7 сценария ([../script.md](../script.md)). Показывает ту же задачу, решённую с учётом четырёх свойств поставки, без привязки к конкретному тяжёлому инструменту CI/CD.

## Задача та же

Развернуть скрипт сопоставления жалоб на сервере ИТ-отдела мэрии: еженедельная сводка специалисту, ежемесячный отчёт общественному совету.

## 1. Версионированный артефакт вместо «отредактировать файлы на сервере»

На сервер разворачивается не рабочая копия репозитория, а конкретный помеченный тегом релиз:

```bash
git tag v0.1.0-pilot   # соответствует ревью из лекции 6
git push origin v0.1.0-pilot

# на сервере:
git fetch --tags
git checkout v0.1.0-pilot
```

В логах и в самом отчёте система указывает свою версию: «Отчёт сформирован системой v0.1.0-pilot». Всегда можно точно сказать, какая версия работает и прошла ли она ревью.

## 2. Конфигурация — отдельно от кода

```bash
# /etc/pilot_increment/config.env (вне репозитория, права доступа 600)
STATION_API_KEY=...
COMPLAINTS_DB_PASSWORD=...
REPORT_EMAIL_SMTP_PASSWORD=...
```

```python
# config.py — читает переменные окружения, не хранит значений
STATION_API_KEY = os.environ["STATION_API_KEY"]
```

Секреты не попадают в репозиторий и не видны при простом просмотре кода. Смена пароля не требует изменения и повторного ревью кода.

## 3. Минимальная наблюдаемость: явная проверка результата, а не только запуска

```bash
run_weekly_summary.sh
```

```python
def run_weekly_summary():
    result = build_summary()
    if result.row_count == 0 or result.has_missing_sources:
        notify_team(f"Сводка за неделю пуста или неполна: {result.diagnostics}")
        sys.exit(1)  # cron заметит ненулевой код возврата
    send_report(result)
    log(f"Отчёт отправлен успешно, версия v0.1.0-pilot, {result.row_count} записей")
```

```cron
0 9 * * 1   /opt/pilot_increment/run_weekly_summary.sh || \
            echo "Сбой еженедельной сводки" | mail -s "ALERT: pilot increment" team@eco-center.local
```

Простое условие — «если результат пуст или неполон, сообщить команде, а не отправлять письмо как обычно» — ловит именно тот класс тихих сбоев, который инструкция AI пропускала.

## 4. Документированный откат

```markdown
# ROLLBACK.md
Если новая версия начала присылать неверные отчёты:
1. `git checkout v0.1.0-pilot` (или предыдущий известный рабочий тег).
2. Перезапустить cron-задание вручную, чтобы убедиться, что откат сработал.
3. Сообщить команде о причине отката в канале #pilot-increment.
4. Завести задачу с разбором причины, прежде чем пробовать новую версию снова.
```

Откат занимает одну команду и не требует «вспоминать», как код выглядел раньше — потому что предыдущая версия уже сохранена как тег.

## 5. Поэтапность

Запуск идёт в три стадии, а не сразу на всех адресатов:

1. **Внутренний тестовый прогон** — результат уходит только в лог, не отправляется никому, в течение первой недели.
2. **Специалисту экологической службы** — только еженедельная сводка, две недели, пока команда убеждается в стабильности.
3. **Общественному совету** — ежемесячный отчёт подключается только после того, как еженедельная сводка отработала стабильно хотя бы дважды подряд.

---

## Сравнение усилий

Реализация этой версии требует примерно на треть больше первоначальной работы, чем инструкция AI (вынесение конфигурации, минимальная проверка результата, документ отката, тег версии). Открытый вопрос для обсуждения на лекции — какая часть этой работы обязательна даже для «всего лишь пилота», а какая могла бы быть отложена без существенного риска.
